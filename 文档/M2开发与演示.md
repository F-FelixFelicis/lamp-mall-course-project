# M2 商品与报价（2026-10-03）

## 演示入口

后端 `http://127.0.0.1:8000/api/docs`；管理员 `http://127.0.0.1:5173`；客户端 `http://127.0.0.1:5174`；商家端 `http://127.0.0.1:5175`。启动步骤见根目录 README。

## 三端操作顺序

1. 商家端注册/登录，填写店铺名称、负责人、联系电话、地址并上传证照，提交认证。
2. 管理端进入“商家认证”，查看证照并通过或填写理由驳回。驳回后商家修改并重提。
3. 商家端进入“商品”，新建灯具，选择分类，添加一个或多个规格及图片；保存草稿后提交审核。
4. 管理端进入“商品资料”，查看规格及图片，通过审核。
5. 商家在商品规格下提交价格、库存与单位。管理端进入“销售报价”审核。
6. 商家点击“上架”。客户端首页显示灯具，支持分类、关键词、价格排序与分页，详情页按规格列出有效报价。
7. 第二家认证商家在“商城选品”搜索商品、选择规格并提交报价；审核通过后同一规格显示两家店的价格。
8. 修改报价时创建新报价；审核通过才替代本店同一规格的旧报价。下架商品后客户不能继续读取详情。

可演示异常分支：无认证提交商品、其他商家操作本店商品、驳回不填理由、使用旧版本提交、伪造图片、其他商家读取私有证照。接口分别拒绝并返回业务错误；页面显示可理解的提示。

## 实现约定

- 所有更新、提交与审核使用 `version` 乐观锁；并发或旧页面操作返回 409，需刷新重试。审核相同版本、相同结论与理由可重复提交，不重复追加审核历史。
- 商品：DRAFT → PENDING → APPROVED → ON_SALE → OFF_SALE。REJECTED 可修改后重新提交；下架后修改资料会回到 DRAFT。审核通过与上架是两个操作。
- 报价：DRAFT → PENDING → ACTIVE；驳回后创建新报价。新报价通过时，旧 ACTIVE 变为 EXPIRED。数据库唯一约束保护“每商家每 SKU 只有一个生效报价”。修改 SKU 后，旧规格的所有在途/有效报价失效。
- 客户只看到已上架、分类有效、创建商家认证有效的商品，并且必须至少有一个商家认证有效、有货、有效期内的 ACTIVE 报价。
- 上传只接受 JPG/PNG/WebP，限制 5 MB 和 2000 万像素；重编码为 JPEG，剥离元数据。证照仅文件所有者或管理员可读，商品图根据商品当前状态动态授权，不生成携带令牌的 URL。
- 审核记录追加保存，操作日志记录主体、对象、状态和 request_id，不记录密码、验证码或证照内容。

## 与 v0.1 设计的细化

`schema.sql` 和 `openapi-v0.1.yaml` 保留为完整系统规划。可执行数据库以 Alembic 迁移为准；实际 M1+M2 接口以 `api/openapi-m2.json` 为准，未实现订单/检索接口不会出现在该文件中。

M2 新增 11 张表，连同 M1 的 3 张表共 14 张业务表。相比设计基线补充了文件 `purpose`、商家 `version`、商家审核 `submitted_version` 和报价 `active_slot`。`active_slot=1` 表示 ACTIVE，其余状态为 NULL；组合唯一键 `(merchant_id, sku_id, active_slot)` 防止同时生效。初始分类为吊灯、吸顶灯、台灯、落地灯、壁灯。

本阶段使用本地文件存储和 SQLite 验证。MySQL 8 迁移语法可生成，但不等于真实 MySQL 已验收。微信小程序编译通过不等于真机验收，仍需 AppID、HTTPS 服务和合法域名配置。

演示图为程序绘制示意图；后续 M4 应单独整理真实灯具图片、来源授权、查询/图库划分和检索指标，不能用本阶段示意图证明算法效果。
